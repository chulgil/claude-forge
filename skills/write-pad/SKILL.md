# Write PAD — 아이디어를 문서로

## 목적

Grill Me 등으로 도달한 공유된 이해를 **구조화된 설계 문서(PAD)**로 변환한다. PAD는 구현의 "목적지"를 설명하는 문서이다.

## 프로세스

사용자가 PAD를 만들고 싶을 때 호출된다. 이전 대화에서 이미 깊은 인터뷰를 했다면 해당 단계는 건너뛸 수 있다.

### 1단계: 상세 설명 수집
사용자에게 길고 상세한 설명을 요청한다.

### 2단계: 코드베이스 검증
코드베이스를 탐색하여 사용자의 주장과 가정을 검증한다.

### 3단계: 인터뷰 (필요 시)
공유된 이해에 도달할 때까지 사용자를 끈질기게 인터뷰한다. (Grill Me와 동일)

### 4단계: 모듈 개요
구현을 완료하기 위해 빌드하거나 수정해야 할 주요 모듈의 개요를 잡는다.

### 5단계: PAD 작성
문제와 솔루션을 완전히 이해하면 아래 템플릿으로 PAD를 작성한다.

## PAD 템플릿

```markdown
# [기능명] PAD

## 문제 정의
[현재 상태와 문제점을 명확히 기술]

## 솔루션 개요
[제안하는 해결 방안의 높은 수준 설명]

## 유저 스토리
- 사용자로서 [행동]하면 [결과]를 얻을 수 있다
- 사용자로서 [행동]하면 [결과]를 얻을 수 있다
- ...

## 수용 기준
- [ ] [유저 스토리 1의 완료 조건]
- [ ] [유저 스토리 2의 완료 조건]
- ...

## 구현 결정 사항
[너무 구체적이지 않게 — 내구성이 있어야 함]
[코드와 PAD가 맞지 않으면 구현 시 문제가 생김]

## 영향받는 모듈
- [모듈 1]: [변경 내용]
- [모듈 2]: [변경 내용]
```

## 사용 시점

- Grill Me 인터뷰 완료 후
- 새 기능 구현을 시작하기 전
- 복잡한 변경의 범위를 명확히 하고 싶을 때

## 주의사항

- 구현 결정 사항은 너무 구체적으로 정하지 않는다 (내구성 우선)
- PAD는 "목적지"를 설명하는 문서이지, "여정"이 아니다
- 여정(작업 분해)은 pad-to-issues 스킬에서 처리
- PAD 완성 후 GitHub Issue로 제출을 권장
