# PAD to Issues — 문서를 작업으로 분해

## 목적

PAD(목적지 문서)를 **독립적으로 작업 가능한 GitHub Issue들(여정)**로 변환한다. 수직 슬라이스 중심으로 분해하여 Unknown Unknowns를 빠르게 드러내고, 병렬 작업을 가능하게 한다.

## 프로세스

### 1단계: PAD 로드
PAD가 컨텍스트 윈도우에 없으면 가져온다.

### 2단계: 코드베이스 탐색
PAD에서 언급된 모듈과 관련 코드를 탐색하여 현재 상태를 파악한다.

### 3단계: 수직 슬라이스 초안 작성
PAD를 개별 작업으로 분해한다. 반드시 **수직 슬라이스** 방식으로 분해한다.

#### 수직 슬라이스란
모든 레이어(DB, API, UI)를 관통하는 얇은 기능 단위. 수평 슬라이스(한 레이어만 작업)가 아님.

```
# 좋음: 수직 슬라이스
이슈 1: 편집 엔진 코어 + 테스트 (모든 레이어 관통) ← Unknown Unknowns 먼저!
이슈 2: 문서 패널 UI (독립, 병렬 가능)
이슈 3: AI 채팅 통합 (이슈 1에 의존)

# 나쁨: 수평 슬라이스
이슈 1: DB 레이어 전체
이슈 2: API 레이어 전체
이슈 3: UI 레이어 전체
```

#### 분해 우선순위
Unknown Unknowns(모르는 것 중 모르는 것)를 빠르게 드러내는 작업을 먼저 배치:
- 새로운 서비스 통합
- 이전에 해본 적 없는 두 시스템 연결
- 접근 방식의 유효성 검증이 필요한 작업

### 4단계: 차단(Blocking) 관계 설정
각 이슈 간의 의존성을 명시한다.
- 차단되지 않는 이슈는 병렬 실행 가능
- QA 이슈나 개선 사항도 추가 가능

```
이슈 1 ──blocks──→ 이슈 3
이슈 2 ──blocks──→ 이슈 4
이슈 1 & 이슈 2: 병렬 가능 ✓
```

### 5단계: 사용자 승인 후 GitHub Issue 생성
각 이슈는 부모 PAD를 참조하고, PAD의 유저 스토리를 수용 기준으로 포함한다.

## 이슈 템플릿

```markdown
# [이슈 제목]

## 부모 PAD
[PAD Issue 링크]

## 설명
[이 수직 슬라이스가 하는 일]

## 수용 기준 (PAD 유저 스토리에서)
- [ ] [관련 유저 스토리 1]
- [ ] [관련 유저 스토리 2]

## 차단 관계
- Blocked by: [이슈 번호] (해당 시)
- Blocks: [이슈 번호] (해당 시)

## 구현 노트
[이 슬라이스에 특화된 기술적 고려사항]
```

## 사용 시점

- PAD 작성 완료 후
- 대규모 기능을 병렬 작업 가능한 단위로 나눌 때
- 아키텍처 개선 RFC를 실행 계획으로 변환할 때

## 주의사항

- 4개 이하의 슬라이스를 목표로 한다 (너무 세분화하지 않음)
- 각 이슈는 독립적으로 테스트 가능해야 한다
- 차단 관계가 순환하지 않도록 주의
