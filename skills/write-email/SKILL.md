# 사내 업무 이메일 작성 스킬

## 사용법

```
/write-email [받는 사람] [용건 요약]
```

예시:
```
/write-email 박성현 상무님에게 프로젝트 진행 현황 공유
/write-email 조연하 기획에게 RP 보정 완료 회신
/write-email 이준성 팀장님에게 다이브인 현황 공유
```

## 실행 절차

### 1단계: 인자 파싱

- 받는 사람 (직급 포함)
- 용건 요약
- 참조자 (있으면)

### 2단계: 참고 이메일 톤 확인

`docs/mars-kr/communication/emails/` 디렉토리 내 기존 이메일을 참조하여 톤을 맞춘다.

### 3단계: 이메일 초안 작성

아래 양식과 규칙을 반드시 따른다.

## 이메일 양식

```
제목: [제목]

보낸 날짜: [날짜]
보낸 사람: 이철길 <chulgil.lee@riman.com>
받는 사람: [받는 사람]
참조: [참조자]

──────────────────────────────────────

[받는 사람 직급] 안녕하세요.
이커머스팀 이철길입니다.

[용건 요약 한 줄 — "~공유드립니다", "~확인 요청드립니다" 등]

■ [섹션 제목 1]

[본문]

■ [섹션 제목 2]

[본문]

 ・[리스트 항목 1]
 ・[리스트 항목 2]

[맺음 요청 — 하나만]

감사합니다.
이철길 드림
```

## 작성 규칙 (18개)

### 양식

1. ■ 섹션 구분자 + ・(나카구로) 리스트 마커
2. 메일 상단에 ────── 구분선 (서명 블록은 그룹웨어에 있으므로 별도 추가 불필요)
3. 인사말: "OOO님 안녕하세요." + "이커머스팀 이철길입니다."
4. 인사 직후 용건 요약 한 줄 필수
5. 맺음 요청은 하나만 — 두 개 이상 연속 금지
6. 맺음말: "감사합니다.\n이철길 드림"

### 톤

7. 마크다운 헤더(##) 사용 금지 — ■ 구분자로 대체
8. 어미: "~하려고 합니다", "~할 예정입니다", "~드립니다" 등 자연스러운 표현
9. 가이드/매뉴얼 형식 금지 — 보고/공유 어조
10. 구현 방식은 상대팀에 맡기는 어조 ("참고해 주시면 되겠습니다")

### 줄바꿈 — 중간 밸런스가 핵심

11. 절(clause) 단위로 끊기 — 쉼표(,) 또는 접속사(-하여, -하고) 뒤가 자연스러운 줄바꿈 지점
12. 한 문장이 3줄 이상 되면 과도 / 모든 문장을 한 줄에 다 붙이면 답답 → 1~2줄이 적정
13. 의미 단위가 바뀌는 곳(다른 주제로 넘어갈 때)은 빈 줄로 문단 분리

### 외부 업체 대상 메일 주의사항

14. 기술 구현 디테일 금지 — "프론트 코드", "index.html", "beforeEach 가드", "vite.config.js" 등 코드 레벨 용어 사용 금지. "수정했습니다", "변경했습니다"로 충분
15. 받는 사람이 관심 없는 정보 제거 — 어떤 파일을 수정했는지가 아니라 **결과(무엇이 바뀌었는지)**만 전달
16. 확인 요청 시 URL/링크를 제시하고 안내 문장 추가 — 리스트만 던지지 말고 "아래 URL에서 확인해 주시면 감사하겠습니다" 등 한 줄 맥락 제공

### 임원 대상 메일 주의사항

17. Jira 티켓 번호 나열 금지 — 에픽 번호만 한 줄로 언급
18. 기술 용어 영어 괄호 최소화 — "조회 전용"이면 충분, "(Read-Only)" 불필요
19. 주어 불명확 금지 — "교육을 진행했고" → "누가 누구에게" 명확히
20. "바빠서 못 해요" 뉘앙스 금지 — "별도 리소스 없이도 자체 운영 가능" 등 긍정적 프레이밍
21. 건수/통계/세부 수치는 본문에 불필요 — 필요시 첨부파일로 분리

### 번호 리스트 구조

22. 번호 제목 바로 아래에 설명 — 제목과 설명 사이에 빈 줄 넣지 않음 (흐름 끊김 방지)
23. 동등한 항목은 번호 리스트 유지 — 별도 ■ 섹션으로 분리하면 덜 중요해 보임
24. ・리스트는 설명 문장 아래에 바로 연결 — 들여쓰기 통일 (앞에 공백 1개)

### 중복 방지

25. 동의어 중복 금지 — "검토 확인", "공유 전달" 등 같은 뜻 단어 나열 금지. 하나만 쓴다
26. 동일 정보 위치 중복 금지 — 수정 내역에서 설명한 내용을 확인 요청에서 반복하지 않는다. 한 곳에서만 말한다
27. 반영 범위 명시 필수 — 운영/테스트 어디까지 반영되었는지 항목별로 명확히 구분한다. 모호하면 전부 운영 반영된 것으로 오해

## 4단계: 저장

작성된 이메일을 해당 프로젝트의 `emails/` 디렉토리에 `YYYYMMDD-[키워드].md` 형식으로 저장한다.

## 5단계: 검증

작성 후 아래 체크리스트로 자체 검증한다.

- [ ] ■ 구분자, ・마커 사용했는가
- [ ] 용건 요약이 인사 직후에 있는가
- [ ] 줄바꿈이 절 단위로 적절한가 (한 줄에 다 붙이지 않았는가 / 3줄 이상 쪼개지 않았는가)
- [ ] 맺음 요청이 하나인가
- [ ] 번호 리스트: 제목 바로 아래 설명인가 (사이에 빈 줄 없는가)
- [ ] 외부 업체 대상이면: 기술 구현 디테일("프론트 코드", "index.html" 등) 없는가, 결과 중심인가
- [ ] 확인 요청 시 URL 제시 + 안내 문장이 있는가 (리스트만 던지지 않았는가)
- [ ] 동의어 중복 없는가 ("검토 확인" 등)
- [ ] 동일 정보가 두 곳에서 반복되지 않는가
- [ ] 반영 범위(운영/테스트)가 항목별로 명확한가
- [ ] 임원 대상이면: 티켓 나열 없는가, 영어 괄호 최소화했는가, 주어 명확한가
